## 0. Честная точка отсчёта

Что есть на 22.09.2026 (panel v0.9.1, agent на Go):

| Слой | Состояние | Проверено на реальной машине |
|---|---|---|
| Вход, 2FA, сессии, step-up, коды восстановления | готово, e2e 78 (api) + 145 (web) | нет — только локально |
| Серверы: добавление, SSH-проверка, установка агента по SSH | код есть | **нет** — FakeSsh в тестах, реального сервера панель ни разу не видела |
| Агент: enroll, heartbeat, метрики по WSS | код есть, релизы в GitHub | **нет** — ни одной реальной ноды под агентом |
| Веб-терминал (ssh2 + xterm) | работает локально против FakeSsh | **нет**; известны лаги |
| Инциденты + автопочинка | детекция и реестр команд есть | **нет** — на фейковых метриках |
| Ассистент + база знаний (zveno.ai) | чат, инструменты read-only, propose_action | **частично** (реальный LLM), но без реальных данных нод |
| Обзор, Журнал, Настройки | по демо | на моках |
| Деплой (compose.yaml, Caddy, Dockerfile api) | заготовка | **нет** — панель нигде не развёрнута |

Вывод: построено много, но **ни один сквозной сценарий не прошёл на живом сервере**. Ощущение
«ничего не доделано» верное именно в этом смысле. Поэтому план перестраивается вокруг одного
правила: **каждая функция считается сделанной только после прогона на реальной машине**.

## 1. Как работаем (правила без исключений)

Для каждой функции цикл один и тот же, порядок фиксирован:

1. **Ресёрч** — как это делают профессионалы (референсы: Coolify, Dokploy, Portainer, Beszel,
   NetBird, Remnawave, Netdata; документация ssh2, xterm, systemd, iptables/nft). Результат —
   короткая записка «что берём / что отклоняем и почему» в `docs/research/<функция>.md`.
2. **Спека** — сценарий «как пользователь это делает» + все состояния экрана: загрузка (скелетон),
   пусто, ошибка, успех, повтор. Без спеки код не пишем.
3. **Реализация** — API + фронт + агент, если нужен. Один pull request на функцию.
4. **Тесты** — unit + e2e на моках (детерминизм), затем **прогон на стенде** (реальная нода).
5. **Состязательное ревью** — минимум 3 независимых агента с разными ролями (корректность,
   безопасность, UX/дизайн) + верификатор, который проверяет каждую находку и отбрасывает ложные.
   Найденное чинится, ревью повторяется до нуля подтверждённых находок.
6. **Скриншоты** — три темы × три ширины (1440 / 1024 / 390), с проверкой скелетонов и пустых
   состояний. Хранятся в `docs/screenshots/`.
7. **Сдача** — чекпоинт из спеки пройден на стенде, раздел открывается в меню
   (`apps/web/src/lib/stages.ts` → `OPEN_SECTIONS`).

Критерий «ноль ошибок»: релиз функции не закрывается, пока (а) все тесты зелёные, (б) ревью не даёт
подтверждённых находок, (в) сценарий прошёл на стенде дважды подряд (чистая установка и повтор).

## 2. Модель безопасности действий AI (основа «Джарвиса»)

Каждое действие панели или ассистента относится к одному из уровней. Уровень зашит в реестре
действий, его нельзя поднять из чата.

| Уровень | Что это | Кто выполняет | Примеры |
|---|---|---|---|
| **T0 Наблюдение** | только чтение | AI автоматически, всегда | метрики, логи, `ufw status`, `ss -s`, `docker ps`, вывод терминала |
| **T1 Безопасное авто** | обратимо, идемпотентно, есть авто-проверка после и авто-откат | AI автоматически, **только если все 4 условия выполнены** | перезапуск контейнера ноды, очистка логов/кеша apt, `ufw reload`, обновление geo-базы |
| **T2 С подтверждением** | меняет конфигурацию или трафик | AI предлагает карточку → ты жмёшь «Да» (step-up) | установка Psiphon/Selfsteal, смена версии Xray, открытие/закрытие порта, обновление агента |
| **T3 Только вручную** | необратимо или задевает доступ | AI **никогда** не выполняет, только подсказывает команду для терминала | `ufw reset`, смена SSH-порта, `rm -rf`, `reboot`, удаление ноды, правка ключей |

Условия для T1 («уверен на 100 %»): 1) действие в белом списке реестра, 2) предусловия проверены
непосредственно перед запуском (агент онлайн, диск не переполнен, нода не в процессе другого
действия), 3) есть пост-проверка с таймаутом («контейнер `Up`, порт слушает»), 4) есть откат
(предыдущее состояние сохранено, откат выполняется автоматически при провале пост-проверки).
Если хоть одно условие не выполняется — действие автоматически понижается до T2.

Каждое действие пишется в Журнал с уровнем, причиной, результатом пост-проверки и откатом.
Тумблер «автопочинка» в настройках включает T1 (по умолчанию выключен, включаем после этапа R3).

## 3. Этапы и функции

Нумерация R («реальность») — чтобы не путать с фазами `roadmap.md` и этапами
`implementation-plan.md`. Разделы меню открываются по мере сдачи; пока открыт только «Серверы».

### R0 — Стенд: панель в интернете, тестовая нода

Без этого ничего нельзя проверить по-настоящему. Оценка: 2–3 дня.

Что нужно от тебя:
- VPS под панель: 2 vCPU / 4 ГБ / 40 ГБ, Ubuntu 24.04, отдельный от нод. Домен, например
  `panel.<твой-домен>`, A-запись на этот VPS.
- Тестовая нода: самый дешёвый VPS (1 vCPU / 1 ГБ), можно пересоздавать. **Не боевые ноды** —
  их подключаем только после сдачи R1.
- Доступы: root-SSH на оба, права на GitHub-репозитории панели и агента, ключ zveno.ai.

Шаги:
1. Проверить `infra/compose.yaml`: сервис `web` отсутствует — решить, как раздаётся статика
   (собранный `apps/web/dist` внутри образа api + `file_server` в Caddy, либо отдельный образ).
   Дописать хвост `Caddyfile` (статика, SPA-fallback), healthcheck web.
2. `infra/scripts/install.sh` по паттерну Coolify: проверка ОС, установка Docker, генерация `.env`
   (`openssl rand`), `docker compose up -d`, вывод setup-токена. И `update.sh` (pull образов,
   миграции, перезапуск). Rollback: предыдущий тег образа сохраняется.
3. CI: `release.yml` собирает образ api в GHCR по тегу; `install.sh` берёт `latest` или тег.
4. Бэкапы: `pg_dump` по cron в volume + инструкция восстановления. Проверить восстановление один раз.
5. Развернуть панель на VPS, пройти мастер первого запуска, 2FA, блокировку, выход — с телефона
   тоже.
6. Агент: проверить, что GitHub Releases `feauche/nodeservice-agent` реально содержат бинари
   amd64/arm64 и `checksums.txt`; если нет — собрать релиз через `release.yml`.
7. Чекпоинт: панель открывается по HTTPS, `docker compose ps` — все `healthy`, перезагрузка VPS не
   ломает стек, бэкап восстанавливается.

### R1 — Серверы: сквозной путь до живой ноды (раздел открыт)

Цель: добавить реальный сервер → SSH работает → агент установлен → метрики живые → терминал
живой. Оценка: 1,5–2 недели, потому что здесь всплывёт большинство расхождений с реальностью.

**1.1 Добавление сервера по SSH**
- Ресёрч: как Coolify/Dokploy хранят и проверяют SSH-доступ (ключ vs пароль, TOFU host-key,
  проверка `sudo`, определение ОС/архитектуры).
- Шаги: проверить `servers.service.ts` против реального ssh2 (таймауты, host-key pinning при первом
  подключении с показом отпечатка, ошибки понятным языком: «неверный пароль», «порт закрыт»,
  «хост-ключ изменился»); определение ОС/арх/CPU/RAM реальными командами; хранение доступов —
  шифрование уже есть, проверить ротацию мастер-ключа.
- Экран: форма с живой проверкой по шагам (подключение → sudo → сбор фактов), скелетон карточки
  сразу после «Добавить», состояние ошибки с кнопкой «Повторить».
- Тесты: e2e с FakeSsh (есть) + прогон на тестовой ноде: пароль, ключ, неверный порт, смена
  host-key.

**1.2 Автопроверка SSH и статус карточки**
- Джоба `ssh-autocheck` на реальных таймаутах; статусы «SSH в порядке / недоступен / проверяется»
  с временем последней проверки; кнопка «Проверить все» с прогрессом по карточкам.

**1.3 Установка агента по SSH**
- Шаги: `install.sh` агента запускается панелью через SSH с одноразовым токеном; прогресс
  установки транслируется в диалог (`agent-install-dialog.tsx`) построчно; обработка провалов
  (нет curl, нет systemd, arm64, нет доступа к GitHub → показать, как поставить вручную).
- Проверить закалку unit-файла (`ProtectSystem=strict`) не мешает метрикам conntrack/сети.
- Повторная установка и «Переустановить агента» — идемпотентно.

**1.4 Канал агент ↔ панель**
- Enroll (токен → ed25519, TOFU), challenge-response, heartbeat, метрики. Проверить через Caddy
  (WSS, таймауты idle, реконнект с backoff при рестарте панели).
- Частоты из настроек реально доезжают до агента.
- Метрики в VictoriaMetrics: CPU/RAM/диск/сеть bps+pps/conntrack/load/uptime — сверить с `top`,
  `ss -s`, `nload` на самой ноде (расхождение > 5 % = баг).

**1.5 Окно сервера с живыми данными**
- Вкладки Метрики/Ёмкость/Настройки на реальных сериях; скелетоны при первой загрузке, «нет данных
  ещё» для новой ноды; графики без прыжков при тике.

**1.6 Веб-терминал как основной инструмент**
- Ресёрч: оптимизация xterm (WebGL-рендерер, batching, flow control), как делают Coolify/Portainer.
- Убрать лаги: буферизация вывода, `StringDecoder`, resize по PTY, копирование/вставка, история,
  переподключение после обрыва без потери окна.
- Окно: свернуть/на весь экран/закрыть, память позиции и размера, несколько вкладок (по ноде).
- Прогон на тестовой ноде: `nodectl`, `htop`, `tail -f`, вставка длинного текста, отключение
  сети на 30 с.

**1.7 Поток терминала для AI («глаза Джарвиса»)**
- Каждая сессия пишет структурированный лог: команда, вывод, код возврата, время (без паролей —
  маскирование ввода при скрытом echo). Хранение с ротацией, доступ только админу.
- Это фундамент R4: ассистент читает поток и даёт подсказки. Здесь только сбор и просмотр
  «Истории терминала» в окне ноды.

**1.8 Обслуживание сервера**
- Обновить сервер (apt), обновить/переустановить агента, удалить сервер (T3, step-up) — всё через
  агента или SSH, с прогрессом и записью в Журнал.

**1.9 Дизайн-проход по разделу** — см. §4. Чекпоинт R1: тестовая нода добавлена с нуля за
< 3 минуты, метрики совпадают с реальными, терминал без лагов 10 минут работы, повторная установка
агента не ломает ничего. После сдачи подключаем **первую боевую ноду** и открываем «Обзор» и
«Журнал» (R2).

### R2 — Обзор и Журнал на реальных данных

- Обзор: KPI и полоса здоровья из реальных метрик; «Требует внимания» из реальных инцидентов;
  «Обслуживание» пока с ручным вводом сроков. Скелетоны на каждый блок.
- Журнал: live-лента через SSE, фильтры, поиск по tsvector, экспорт. Проверить партиции и
  retention.
- Чекпоинт: сутки работы с 2–3 нодами без единой ошибки в логе api.

### R3 — Инциденты и автопочинка на реальных нодах

- Детекция на реальных порогах с гистерезисом, тайм-лайн инцидента, ручное закрытие.
- Реестр действий с уровнями T0–T3 (§2): пред-условия, пост-проверка, откат. Первые T1-действия:
  перезапуск ноды, освобождение диска, `ufw reload`.
- Пресеты автопочинки включаются по одному после недели наблюдений на тестовой ноде.
- Чекпоинт: искусственно созданный инцидент (забить диск, положить контейнер) чинится сам, в
  Журнале полный след, откат срабатывает при подстроенном провале пост-проверки. Открываем
  «Инциденты».

### R4 — Ассистент = Джарвис (открываем «Ассистент» и «База знаний»)

- Контекст ассистента: метрики, инциденты, поток терминала (1.7), Журнал, база знаний, факты о
  ноде (ОС, установленное, версии).
- **Подсказки в терминале**: боковая панель у окна терминала — ассистент комментирует вывод
  («это conntrack упёрся в лимит, вот что можно»), предлагает следующую команду, ты вставляешь
  одной кнопкой. Ничего не выполняет сам.
- Инструменты по уровням §2: T0 читает, T1 выполняет сам (если тумблер включён), T2 создаёт
  карточку-предложение с объяснением и оценкой вероятности, T3 только текст команды.
- Плейбуки диагностики: нода офлайн, ТСПУ-деградация (падение скорости/ретрансмиты/RST по
  порту), блокировка домена в РКН, Gemini видит RU, забитый conntrack, забитый диск.
- Уровни пользователя (новичок/средний/эксперт) влияют на подробность.
- Чекпоинт: 10 сценариев на тестовой ноде — ассистент правильно называет причину и предлагает
  верное действие в ≥ 9; ни одного самовольного T2/T3.

### R5 — Проверки, блокировки, Настройки (открываем «Настройки»)

- Скорость канала, гео-разметка IP, реестр РКН, признаки ТСПУ, доступность RU/зарубежных
  сервисов — по расписанию с тумблерами; методы в `checks-and-blocking.md`.
- Настройки: единый экран со всеми токенами и расписаниями, всё сохраняется в БД, секреты
  шифруются.

### R6 — Уведомления

- Колокол в панели + Telegram (бот, прокси SOCKS5/HTTP), дедупликация, тихие часы.

### R7 — Утилиты и пресеты

- Установка через агента наших `remnanode-installer` и `web-proxy-tg-installer`, тумблеры
  IPv6/ICMP/геоблок/SYNPROXY, версия Xray. Прогресс живой, идемпотентно, T2.

### R8 — База знаний-харвестер, ёмкость, биллинг

- Telegram-харвестер (режим бота по умолчанию, userbot с предупреждением), расчёт ёмкости по
  реальным метрикам, сроки доменов/сертификатов/оплат.

## 4. Дорожка дизайна (сквозная, обязательна для каждого этапа)

Требования владельца (22.09.2026): удобство в первую очередь, потому что пользоваться будет он
сам; скелетоны на всех загрузках и обновлениях; симметрия и параллельность кнопок; всё «под
рукой»; эффект «всё на своих местах».

Правила, которые проверяет дизайн-ревьюер на каждом экране:
1. **Четыре состояния у каждого блока данных**: скелетон (форма повторяет будущий контент, без
   прыжков высоты), пусто (что делать дальше, одна кнопка), ошибка (что случилось + «Повторить»),
   данные. Обновление на тике — без мигания и без пересоздания DOM.
2. **Симметрия**: кнопки одной группы одной высоты и ширины, выровнены по сетке 4 px; главное
   действие одно на экран и справа; второстепенные — слева от него, одинаковые.
3. **Плавность**: переходы 150–200 мс, `prefers-reduced-motion` уважается; ничего не вылезает за
   рамки на 390 / 1024 / 1440 px; нет горизонтального скролла.
4. **Под рукой**: частые действия (терминал, перезапуск, проверить) доступны с карточки, из ⌘K и с
   клавиатуры; не больше двух кликов до любого действия ноды.
5. **Один язык**: одинаковые слова для одинаковых вещей («Проверить», «Обновить», «Перезапустить»),
   одинаковые иконки, одинаковые бейджи статусов.
6. **Скриншот-контроль**: три темы × три ширины на каждом этапе, сравнение с предыдущими.

Каждый этап заканчивается отдельным «дизайн-проходом» (пункт x.9), который ревьюится отдельным
агентом со скриншотами, а не по коду.

2. Я: R0 целиком — compose/Caddy/install.sh/update.sh/бэкапы, релиз агента, развёртывание,
