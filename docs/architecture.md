# NodeService — Архитектура фундамента (MVP)

Дата: 2026-08-26 · Статус: черновик на утверждение

Это спецификация **первого под-проекта** — «Фундамент». Остальные модули
(пресеты, ёмкость, авто-починка, AI, уведомления) получат свои спеки позже и
встанут на эту основу. Дорожная карта: [`roadmap.md`](roadmap.md).

---

## 1. Назначение и границы

**Задача MVP:** дать хозяину надёжную основу — добавить сервер, безопасно
подключиться, открыть терминал в браузере и видеть живые метрики. Всё «вау» —
авто-починка и AI — строится потом на этих данных.

**Контекст:** один администратор, десятки+ серверов, самохостинг. Ставится
одной командой (Docker Compose). Дизайн — тёмная графитовая «пультовая» тема
(см. [`../design/preview.html`](../design/preview.html)).

**Входит в MVP:**
- Инвентарь серверов (добавить/редактировать/удалить, группы, статус).
- Безопасное хранение SSH-доступов (ip/логин/пароль/ключ/порт), шифрованно.
- Установка агента на ноду (по SSH, одной кнопкой).
- Живой канал агент↔панель (метрики + команды).
- Базовый мониторинг: CPU (по ядрам), RAM, сеть, диск, conntrack, аптайм.
- Веб-терминал (SSH в перемещаемом окне).
- Одна учётка администратора, вход по паролю + 2FA (TOTP).

**НЕ входит в MVP (следующие фазы):** пресеты установки, оценка ёмкости,
авто-починка, AI-чат, Telegram-уведомления, база знаний (Telegram-харвестер),
мультипользователи/роли.

**Метрики — с самого начала честные и полные.** Агент MVP снимает не только
CPU/RAM/сеть, а весь набор: CPU по ядрам, RAM/swap, диск и IO, сеть vs лимит
порта, `conntrack`, PPS, файловые дескрипторы, load average, GPU (если есть),
число активных соединений. Это реальные замеры (не оценки), с уровнем критичности
у каждого — фундамент для честной оценки ёмкости (Фаза 3) и AI (Фаза 5). В UI
каждый технический термин сопровождается пояснением простым языком.

**Данные растут; AI со сквозным доступом (последующие фазы).** Кроме Postgres
(инвентарь) и VictoriaMetrics (метрики) закладываем **векторную БД** под большую
базу знаний (Фаза 7). AI-ассистент (Фаза 5) получает сквозной доступ на чтение
метрик/логов и на запуск проверок/действий на нодах и в сервисах — **безопасные
автоматически, критичные с подтверждением**. Варианты решений AI берёт из
встроенного плейбука + базы знаний, а при подключённом Telegram-userbot — ещё и
из свежих практик в чатах.

## 2. Компоненты

### 2.1 Panel (backend) — `panel/`
NestJS (TypeScript). Отвечает за: REST API, WebSocket-шлюзы, авторизацию,
хранение, оркестрацию задач. Модули:
- **auth** — мастер первого запуска (setup-токен), вход по паролю + обязательная
  TOTP-2FA, коды восстановления, серверные сессии в Redis (список/отзыв),
  доверенные устройства, throttling, step-up, Rescue CLI. Детали — §5.1.
- **servers** — CRUD инвентаря, шифрование/дешифрование доступов.
- **agents** — регистрация агентов, приём метрик, отправка команд (WS).
- **terminal** — WebSocket-шлюз SSH (библиотека `ssh2`), проксирование PTY.
- **metrics** — запись в VictoriaMetrics, отдача агрегатов фронту.
- **provisioning** — установка агента на ноду по SSH (первичный bootstrap).
- **jobs** — очередь (BullMQ): health-check, переустановка агента, ретраи.

### 2.2 Agent (на ноде) — отдельный репозиторий `nodeservice-agent`

> Решение 2026-08-29: агент живёт в **своём git-репозитории** со своими релизами
> (GitHub Releases: статические бинарники linux/amd64, linux/arm64 + checksums,
> `install.sh`, systemd-юнит). Панель ставит его на сервер по SSH командой
> `curl -fsSL <releases>/install.sh | bash -s -- --panel <url> --token <enroll>`
> и обновляет из релизов. Протокол панель↔агент версионирован (номер версии в
> рукопожатии); в монорепо панели остаётся только контракт протокола.
Go, один статический бинарь, минимальный footprint (работает и на 512 МБ VPS).
- **Сам инициирует** исходящее соединение к панели (WSS) — на ноде не нужен
  открытый входящий порт, работает за NAT и при смене IP.
- Периодически шлёт метрики (частота настраивается).
- Принимает и выполняет команды от панели (применить тумблер, перезапуск и т.п.)
  строго из белого списка операций.
- Регистрируется по одноразовому токену, дальше — mTLS/короткоживущие креды.
- Ставится и обновляется установочным скриптом (по SSH с панели).

### 2.3 Web (фронтенд) — `web/`
React + Vite. «Пульт»: сетка серверов, деталь ноды с графиками, тумблеры,
перемещаемое окно терминала (xterm.js). Дизайн-система — Tailwind + shadcn/ui,
графики — на SVG/Canvas. Всё по токенам темы (тёмная по умолчанию).

### 2.4 Данные
- **PostgreSQL** — сервера, доступы (шифрованно), агенты, пользователь, аудит.
- **VictoriaMetrics** (single-node) — временные ряды метрик (эффективна по RAM
  на десятки+ серверов, Prometheus-совместима).
- **Redis** — очередь задач (BullMQ) и краткоживущий кэш/сессии.

### 2.5 Инфраструктура — `infra/`
Docker Compose: panel + postgres + redis + victoriametrics + **Caddy**
(reverse-proxy с авто-HTTPS). Установка одной командой (скрипт генерирует `.env`
с секретами через `openssl rand`). Агент — отдельный артефакт на ноды.

## 3. Модель данных (черновик)

- **user** — id, логин, argon2id-хэш пароля, totp_secret (шифрован),
  totp_confirmed, totp_last_step, password_changed_at, created_at.
- **recovery_code** — user_id, argon2id-хэш, used_at (10 штук, одноразовые).
- **session** — в Redis: sid → user_id, created_at, last_seen, absolute_expires,
  ua, ip, trusted; в Postgres — зеркало для списка «Активные сессии».
- **trusted_device** — user_id, token_hash, ua, ip_prefix, created_at,
  expires_at (30 дней, max 5).
- **login_attempt** — ip, login, ts, result (для throttling и аудита; TTL).
- **setup_token** — hash, created_at, used_at (один; печатается установщиком).
- **server** — id, имя, локация, группа, статус, теги, created_at.
- **credential** — server_id, тип (password|key), зашифрованные поля
  (host, port, user, secret), алгоритм, created_at. Шифрование — на уровне
  приложения (envelope encryption мастер-ключом из `.env`/KMS).
- **agent** — server_id, agent_id, публичный ключ/отпечаток, версия, last_seen,
  канал (online/offline), enroll_token (одноразовый).
- **metric** — в VictoriaMetrics: `metric{server="…",core="…"} value ts`.
- **audit_log** — кто, что, когда, откуда (ip/ua), результат: вход/выход/попытка,
  сессии, пароль/2FA/коды, allowlist, команда, терминал-сессия, изменение.
- **terminal_session** — server_id, начата/завершена, путь к записи (asciicast).

## 4. Ключевые потоки

**Добавить сервер → поставить агента**
1. Админ вводит ip/порт/логин/пароль(или ключ). Панель шифрует и сохраняет.
2. Кнопка «Установить агента»: панель по SSH качает и запускает bootstrap-скрипт,
   передаёт URL панели + одноразовый enroll-токен.
3. Агент стартует, звонит панели по WSS, регистрируется по токену → получает
   рабочие креды (mTLS). Токен гасится. Сервер загорается «online».

**Живые метрики**
1. Агент шлёт метрики по WSS с настроенной частотой.
2. Панель пишет их в VictoriaMetrics и ретранслирует в браузер (WS/SSE) для
   живых графиков. История берётся запросами к VictoriaMetrics.

**Веб-терминал**
1. Браузер открывает WS к панели (terminal-шлюз).
2. Панель поднимает SSH-сессию (`ssh2`) к ноде, соединяет PTY ↔ xterm.js.
3. Ввод/вывод логируется в запись сессии (asciicast) для аудита.

**Вход администратора**
1. Логин + пароль → проверка throttling (IP + логин) → argon2id → единый ответ
   «Неверный логин или пароль» при любой ошибке.
2. Если cookie доверенного устройства валидна и «всегда спрашивать 2FA»
   выключено — сразу сессия; иначе шаг TOTP (или код восстановления).
3. Создаётся серверная сессия (Redis) + cookie `__Host-sid`; запись в аудит;
   уведомление в Telegram («Это не я» → завершить все сессии).
4. Первый запуск вместо п.1: `/setup` с setup-токеном → создать админа →
   привязать TOTP → показать коды восстановления → сессия.

## 5. Безопасность

- **Доступы не хранятся в открытом виде** — envelope encryption; мастер-ключ вне
  БД (`.env`/KMS). В перспективе — эфемерные SSH-сертификаты (свой SSH CA).
- **Агент-аутентификация** — одноразовый enroll-токен → mTLS для рабочего канала.
- **Канал только исходящий с ноды** — меньше поверхность атаки, работает за NAT.
- **Аудит** — вход, каждая команда, записи терминальных сессий.
- **Панель за Caddy** — авто-HTTPS; сама панель слушает `127.0.0.1`.
- **2FA (TOTP)** обязательна для входа администратора; полная схема
  авторизации — §5.1.

### 5.1 Авторизация администратора (детально)

Ориентиры: OWASP Cheat Sheets, NIST 800-63B rev.4, RFC 6238; референсы — Remnawave
(Rescue CLI, passkeys, stateless JWT без ревокации — это мы делаем лучше), Coolify
(TOTP + recovery-коды), Portainer (setup-окно, session lifetime в настройках).
UI-эталон: экран входа / 2FA / первый запуск / «Безопасность и доступ» в
[`../design/preview.html`](../design/preview.html); требования — `requirements.md` §23.

- **Учётка.** Одна, создаётся мастером первого запуска. Маршрут `/setup` открыт
  только пока админа нет и требует **setup-токен**, который печатает установщик и
  `docker logs nodeservice` (паттерн Jenkins/Grafana; закрывает окно захвата
  инстанса между стартом и первой регистрацией, без 5-минутного таймаута как у
  Portainer). До подтверждения TOTP пользователь в БД не создаётся — логин, хэш
  пароля и зашифрованный секрет живут в pending-записи (Valkey, 10 мин), а в БД
  всё пишется одной транзакцией на `/setup/confirm`; брошенный мастер можно
  начать заново тем же токеном. После создания админа `/setup` → 404 навсегда.
  Неинтерактивная установка: `ADMIN_PASSWORD_FILE`.
- **Пароль.** Argon2id `m=128 MiB, t=3, p=4` (у нас один пользователь — дорогой
  хэш бесплатен) + pepper (argon2 `secret`) из env, отдельно от БД: `PASSWORD_PEPPER`
  (hex), а если не задан — HKDF-SHA256 от `APP_SECRET`. Политика по NIST: ≥12 символов,
  ≤128+, любые символы, без правил композиции и принудительной ротации; проверка
  по офлайн-списку утечённых паролей (top-100k), HIBP k-anonymity — опционально.
- **2FA (TOTP, обязательна).** RFC 6238: SHA-1, 6 цифр, шаг 30 с, окно ±1;
  хранить `last_used_step` и отклонять код со step ≤ последнего (anti-replay).
  Секрет шифруется ключом из env. Включённой считается только после
  подтверждения кодом. Перевыпуск — через step-up (пароль ещё раз).
- **Коды восстановления.** 10 × 10 символов base32 без похожих букв
  (`xxxxx-xxxxx`), только argon2id-хэши, одноразовые, показ один раз.
  Использование = событие безопасности: уведомление, сброс доверенных устройств,
  предложение перевыпустить при остатке ≤3.
- **Сессии — серверные** в Redis: 128-битный id из CSPRNG, cookie
  `__Host-sid` HttpOnly + Secure + SameSite=Strict + Path=/. Idle-TTL 30 мин
  (настраивается; трафик SSH-терминала = активность), абсолютный TTL 12 ч, для
  доверенного устройства — 7 дней. Logout = удаление ключа + истёкшая cookie.
  Смена пароля / перевыпуск 2FA / recovery-код инвалидируют все остальные
  сессии. Список сессий с «Завершить» и «Завершить все, кроме текущей».
- **CSRF.** Synchronizer token на все изменяющие запросы (SameSite — только
  defense-in-depth). WebSocket терминала: проверка `Origin` на handshake +
  короткоживущий одноразовый ticket, выданный по сессии (cookie в URL не
  передаём). Строгий CSP без `unsafe-inline`; секреты только в HttpOnly cookie,
  ничего в localStorage.
- **Антибрутфорс — throttling, не lockout.** По IP и по логину одновременно:
  после 5 неудач задержка 30 с → 1 мин → 5 → 15 (cap 1 ч), сброс через час
  тишины или после успеха. Постоянной блокировки нет (одним известным логином
  нельзя устроить self-DoS). Отдельный лимит на TOTP/recovery: 5 попыток на
  логин-сессию → назад к паролю. Одинаковый ответ и тайминг для неверного
  логина и пароля. `trust proxy` = 1 hop (Caddy), иначе все IP = 127.0.0.1 и
  лимит по IP молча ломается (кейс Coolify GHSA-688j-rm43-5r8x).
- **Доверенные устройства («не спрашивать код 30 дней»).** Отдельная cookie
  `__Host-td` с 256-битным токеном, в БД — хэш + UA + префикс IP + даты; 30 дней
  без авто-продления, максимум 5; список и «Забыть» в настройках; массовый
  отзыв при смене пароля / перевыпуске 2FA / recovery-коде. Пропускает только
  2FA, не пароль. Тумблер «всегда спрашивать 2FA» отключает механизм.
- **Step-up.** Чувствительные действия (смена пароля, перевыпуск 2FA, новые
  коды, allowlist, API-токены) — повторный ввод пароля, действует 5 минут.
- **IP allowlist.** Рекомендуемый уровень — Caddy (`@allowed remote_ip …` →
  статичная страница «Доступ с этого IP запрещён. Ваш IP: … Восстановить:
  Rescue CLI»), плюс проверка в приложении. При сохранении текущий IP
  добавляется автоматически (или явное подтверждение); CIDR и IPv6.
- **Блокировка экрана.** Клиентский оверлей через N минут бездействия — UX;
  реальную защиту даёт серверный idle-TTL. Разблокировка = пароль с проверкой на
  сервере. Истёкшая сессия → полный вход с сообщением «Сессия истекла».
- **Telegram — только уведомления** (вход, серия неудач, смена пароля, новое
  доверенное устройство, recovery-код, изменение allowlist/настроек TG), не
  фактор входа. Chat ID из allowlist. Отправка асинхронно с таймаутом через
  `TELEGRAM_PROXY` (SOCKS5/HTTP) или self-hosted bot-api — недоступность
  api.telegram.org не должна блокировать вход. В сообщении кнопка «Это не я» —
  одноразовая подписанная ссылка «завершить все сессии», после перехода — пароль.
- **Rescue CLI** (`docker exec -it nodeservice cli`): сброс пароля, отключение
  2FA, очистка allowlist, завершение всех сессий, новый setup-токен. Только из
  консоли сервера. Как у Remnawave — единственный резервный канал.
  `reset-password <login>` не принимает пароль аргументом (виден в `ps` и истории
  shell): интерактивно спрашивает в терминале, либо `--password-file <path>`
  (первая строка), либо `echo "$PASS" | cli reset-password admin`.
  `setup-token` работает, пока нет администратора с подтверждённым TOTP.
- **Аудит.** Успешный/неуспешный вход (с причиной: пароль / 2FA / allowlist /
  throttle), logout, отзыв сессии, смена пароля, 2FA, коды, recovery-код,
  allowlist, Telegram-настройки, старт SSH-сессии на ноде. IP + UA + время,
  retention 90 дней, экспорт JSON. В UI — общий Журнал с меткой «безопасность».
- **Позже.** WebAuthn/passkeys как второй вариант подтверждения (резерв к TOTP,
  паритет с Remnawave); API-токены (показ один раз, хэш, срок, step-up, отзыв)
  — если понадобятся внешним скриптам.

## 6. Дизайн-язык (обязательное требование)

Тёмная графитовая тема (с лёгким синим уклоном нейтралей), скруглённые блоки,
плавные и **симметричные** перестроения при изменении ширины, ничего не выходит
за рамки (обрезка текста, скролл внутри карточек). Метрики — красивые графики,
гейджи, спарклайны; статусы — цветом (ок/внимание/критично отдельно от акцента).
Шрифты: Archivo (заголовки), IBM Plex Sans (текст), IBM Plex Mono (данные,
терминал). Референс — [`../design/preview.html`](../design/preview.html).

## 8. Нефункциональные требования

- Десятки+ серверов без деградации UI (пагинация/виртуализация списков).
- Метрики realtime с шагом ~1–3 c; история — минимум 30 дней.
- Панель поднимается одной командой на чистом Ubuntu/Debian.
- Агент не мешает работе ноды (низкий CPU/RAM, лимиты).

## 9. Открытые вопросы (уточнить перед реализацией)

1. Хостинг панели: отдельный сервер только под панель, или на одном из рабочих?
2. Формат доступов: чаще пароль или ключи? (влияет на UX добавления сервера)
3. Хранить ли записи терминальных сессий по умолчанию (аудит vs приватность)?
4. Имя/бренд продукта (сейчас рабочее — «NodeService»).
5. Авторизация: allowlist IP по умолчанию (фиксированный IP или мобильный?);
   доступ из РФ напрямую (прокси для Telegram); passkey в v1 или позже;
   API-токены в MVP; step-up перед SSH-терминалом; абсолютный срок сессии
   12 ч vs 7 дней; второй пользователь/роли когда-нибудь? (см. requirements §16.6–16.12)
