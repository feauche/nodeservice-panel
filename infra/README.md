# infra — установка и обслуживание панели

Стек в `compose.yaml`: Caddy (авто-HTTPS, HTTP/3) → api (NestJS + собранный фронт в `public/`),
Postgres 18, Valkey 8. Наружу открыты только 80/443 у Caddy — или ваш nginx/Caddy, если панель
поставлена рядом с ним (см. ниже).

## Установка одной командой (чистый Ubuntu 24.04 / Debian 12, root)

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/feauche/nodeservice-panel/main/infra/scripts/install.sh)
```

Первым вопросом скрипт спросит, как вы будете открывать панель: **по домену из интернета** (дальше —
как описано ниже) или **только во внутренней сети** (см. «Без домена — только во внутренней сети»).

По домену скрипт спросит домен и почту для сертификатов и сначала покажет сводку по серверу: память и диск,
Docker, куда указывает домен, кто держит порты 80 и 443 (TCP и UDP), есть ли nginx или Caddy и
сертификат. Потом сам выберет способ открыть панель и задаст только вопросы «да/нет»; до ответа
«Начать?» ничего не меняет:

| На сервере | Что делает установщик |
|---|---|
| порты 80/443 свободны | свой Caddy панели на 80/443, сертификат — сам |
| ваш nginx | сайт панели в `sites-available/nodeservice` (или `conf.d/nodeservice.conf`); спросит про бесплатный сертификат Let's Encrypt (certbot, продление — само) или предложит найденный; настройки nginx проверяет до и после, при ошибке возвращает копию |
| ваш Caddy (служба) | `import /etc/caddy/nodeservice.caddy` в конце Caddyfile, сертификат выпускает ваш Caddy |
| Caddy в контейнере (как у Remnawave) | блок сайта между метками в его Caddyfile, api подключается к сети контейнера (`compose.docker-proxy.yaml`) |
| нода с VPN на 443 | объяснит, почему лучше отдельный сервер; по «да» — свой Caddy на 80 и 8443 |
| другая программа на 80/443 | предложит остановить её (по умолчанию — нет) или поставить панель на отдельный сервер |

В способах «рядом с вашим веб-сервером» свой Caddy не запускается, а api слушает только
`127.0.0.1:3080` (`compose.host-proxy.yaml`). Способ записан в `infra/.env` (`PANEL_PROXY` и др.):
по нему `nodeservice`, `update`, `backup` и `restore` берут нужные файлы compose
(`scripts/compose-args.sh`), а `nodeservice uninstall` убирает сайт панели из вашего nginx/Caddy.

Дальше — как раньше: Docker, код в `/opt/nodeservice` (если репозиторий приватный, покажет
deploy-ключ для Settings → Deploy keys), последний стабильный релиз, `infra/.env` с секретами,
сборка api, запуск, команда `nodeservice`. В конце установщик сам открывает https://домен и пишет
«Готово» только если отвечает панель; иначе — что не так и что сделать. Подробности каждого шага —
в `/var/log/nodeservice-install.log`. Повторный запуск сохраняет `.env` и данные, способ открытия
и порт, а образ той же версии не пересобирает. Без вопросов (ответы по умолчанию):
`NODESERVICE_YES=1 NODESERVICE_DOMAIN=домен`.

Нужен домен с A-записью на сервер — или установка во внутреннюю сеть, без домена (см. ниже).

## Требования к серверу

| | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 1 ядро | 2 ядра |
| Память | 1 ГБ (сводка покажет 0,9 — часть берёт система) и 2 ГБ подкачки | 2 ГБ |
| Свободно на диске | 10 ГБ | 20 ГБ |
| Система | чистый Ubuntu 24.04 или Debian 12, доступ `root` | |
| Сеть | выход в интернет: для установки — GitHub, Docker Hub, npm; для работы — Telegram, Remnawave, Check-Host | |

Откуда числа (замер 0.107.1 на чистой Ubuntu 24.04):

- **Сборка** — самое тяжёлое. Панель собирается на сервере 3–8 минут; проверке кода интерфейса нужно около
  1 ГБ памяти, всей сборке — до 1,2 ГБ. На сервере с 1 ГБ недостающее даёт подкачка: если памяти и подкачки вместе меньше 3,5 ГБ,
  установщик сам добавит файл подкачки на 2 ГБ (`/swapfile`). На подкачке сборка медленнее, но проходит.
- **Работа.** В простое панель занимает около 200 МБ: api ~140 МБ, Postgres ~40 МБ, Valkey ~5 МБ. Под
  нагрузкой больше, предел в `compose.yaml` — api 768 МБ, Postgres 512 МБ, Valkey 192 МБ. С 2 ГБ памяти
  панели не приходится уходить в подкачку.
- **Диск.** После установки занято около 6 ГБ: Docker и образы ~1,5 ГБ, кэш сборки ~3 ГБ (обновление удаляет
  кэш старше недели), подкачка 2 ГБ. Дальше растут база, Журнал и резервные копии (см. «Что растёт и как
  чистится») — поэтому рекомендуется 20 ГБ.

Сводка установщика предупреждает знаком «!», если памяти меньше 0,75 ГБ (сервер «на 1 ГБ» показывает около
0,9 — это нормально) или свободного места меньше 10 ГБ.

## Если установка не удалась

Установщик пишет, на каком шаге остановился, почему и что сделать; подробности — в
`/var/log/nodeservice-install.log`. Повторный запуск той же командой безопасен: сделанное (Docker, подкачка,
скачанный код и пакеты) заново не делается, `.env` и данные сохраняются.

| Сообщение | Причина | Что сделать |
|---|---|---|
| «Сборке панели не хватило памяти» | памяти меньше, чем нужно сборке, и подкачка не помогла (например, в контейнере LXC её нельзя создать) | добавить серверу памяти (в Proxmox — в настройках машины) или подкачки и запустить установку снова |
| «…не хватило памяти, хотя у сервера … — этого хватает» | сборке тесно в её собственном пределе (2 ГБ) — ошибка панели | сообщить о ней |
| «Сборку остановила система: не хватило памяти, хотя сервер видит …» | у машины или контейнера свой предел памяти меньше видимого (например, контейнер LXC в Proxmox) | увеличить этот предел и запустить снова |
| «Во время сборки закончилось место на диске» | свободного места меньше 10 ГБ (или осталось меньше 2 ГБ, когда сборка упала) | освободить место и запустить снова |
| «Сборке не удалось скачать нужное из интернета» | нет выхода в интернет, не работает DNS или Docker Hub временно ограничил скачивание | проверить сеть; при ограничении Docker Hub — повторить через час |
| «Сборка панели не удалась» | другая ошибка | установщик покажет последние строки журнала — пришлите их |

До 0.107.1 сборка падала на сервере с 1 ГБ памяти даже с подкачкой: Node ограничивал себе память по
оперативной (около 500 МБ) и подкачкой не пользовался — в журнале `JavaScript heap out of memory`. Теперь
сборке разрешено до 2 ГБ (`NODE_OPTIONS` в `apps/api/Dockerfile`), недостающее берётся из подкачки.
`nodeservice update` на тестовую версию (`main`), которая собирается на сервере, объясняет те же причины.

## Без домена — только во внутренней сети

Для сервера без публичного адреса (например, виртуальная машина на выделенном сервере за NAT, вход через
VPN или проброс порта по SSH). На первый вопрос ответьте «2 — только во внутренней сети»: скрипт найдёт
внутренние адреса сервера (10.*, 172.16–31.*, 192.168.*, 100.64–127.*), предложит первый и поставит панель
на него по http — порт 80, а если он занят, первый свободный с 8080. Домен, почта и сертификат не нужны.

- Где панель слушает (`compose.internal.yaml`: свой Caddy не запускается, api на
  `PANEL_LOCAL_BIND:PANEL_LOCAL_PORT`):
  - у сервера нет ни одного адреса из интернета (виртуальная машина за NAT) — на всех его адресах
    (`PANEL_LOCAL_BIND=0.0.0.0`): во внутренней сети и по адресу VPN на сервере (NetBird, Tailscale, WireGuard),
    в том числе поставленного после установки;
  - адрес из интернета есть — только на выбранном внутреннем адресе, иначе панель без шифрования открылась бы
    всему интернету.

  Адрес панели — `PANEL_PUBLIC_URL` (`http://10.10.10.104`), в `PANEL_DOMAIN` записан тот же адрес.
- Telegram, Remnawave, Check-Host и проверки DPI работают как обычно: панель сама выходит в интернет,
  к ней никто не подключается. Кнопок «Открыть в панели» под сообщениями Telegram нет.
- Открыть снаружи:
  - VPN на сервере и на своём компьютере (NetBird, Tailscale): `http://адрес-сервера-в-VPN` — если панель
    слушает все адреса. Адрес сервера в NetBird виден на сайте NetBird в списке устройств или по `netbird status`;
  - VPN в эту сеть — `http://10.10.10.104`;
  - проброс порта по SSH (Termius и т. п.) — `ssh -L 8080:10.10.10.104:80 root@сервер-с-доступом-в-сеть`,
    затем `http://localhost:8080`.
- Повторный запуск, `nodeservice update`, копии и `install.sh --restore` помнят способ и адрес;
  `update` после обновления проверяет `http://адрес/api/health/live`. Если прежний порт за это время
  занял кто-то другой, повторный запуск переносит панель на свободный и пишет новый адрес.
- Панель, установленная до 0.107.2, слушает только выбранный адрес. Чтобы она открывалась и по адресу VPN,
  запустите установку снова (если у сервера нет адреса из интернета, она сама перейдёт на все адреса) или
  поставьте в `infra/.env` `PANEL_LOCAL_BIND=0.0.0.0` и выполните `nodeservice start`.
- Если панель слушает только один адрес, его лучше брать у сетевой карты сервера. Адрес VPN (NetBird,
  Tailscale, WireGuard) после перезагрузки появляется позже Docker, и панель может не встать сама — тогда
  `nodeservice start`.
- Если у сервера, где панель слушает все адреса, потом появится адрес из интернета, запустите установку снова —
  она вернёт панель на один внутренний адрес.

Без вопросов: `NODESERVICE_YES=1 NODESERVICE_ADDRESS=10.10.10.104 [NODESERVICE_PORT=80]`.

## Обслуживание — команда `nodeservice`

| Команда | Что делает |
|---|---|
| `nodeservice status` | контейнеры, версия кода |
| `nodeservice preflight` | проверка перед обновлением: количество записей, наличие настроек и локальные старые службы; только чтение |
| `nodeservice logs [api]` | логи |
| `nodeservice update [ref]` | выбор релиза → копия перед обновлением (если включена) → загрузка и проверка release-образа → перезапуск → проверка, что панель открывается по https (если нет — предупреждение); `nodeservice update main` собирает тестовую ветку; миграции применяет api при старте |
| `nodeservice rollback` | вернуть предыдущий образ api |
| `nodeservice backup [--to user@host:/dir]` | архив `nodeservice-backup-<время>.tar.gz` (дамп БД + `.env` + meta) в `/opt/nodeservice/backups`; хранение архивов задаётся в панели; `--to` — копия по scp или в папку |
| `nodeservice restore <файл> [--yes]` | восстановить из архива на работающей панели: секреты из бэкапа переносятся в `.env`, БД заменяется (прежняя сохраняется как `nodeservice_pre_restore_*`), api перезапускается. Файл — путь или имя копии из списка панели (ищется в `backups/`). Здесь вход после восстановления — пароль и код установки, с которой сделана копия. Перенести копию со старой панели можно и без консоли: «Настройки → Резервные копии → Восстановить из файла» — панель зашифрует данные копии своими ключами, а вход оставит нынешний |
| `nodeservice cli setup-token` | rescue CLI: `setup-token`, `list-users`, `reset-password`, `disable-2fa`, `revoke-sessions`, `unblock-login` (снять паузы входа после неудачных попыток) |
| `nodeservice uninstall` | снять панель: бэкап БД и `.env` в `/root/nodeservice-last-backup`, затем сайт панели в вашем nginx/Caddy (если был), контейнеры, образы, тома, `/opt/nodeservice`, cron и сама команда. Docker, deploy-ключ и ваши сайты остаются |

`infra/.env` — единственное место с секретами. Без `ENCRYPTION_KEY` из него зашифрованные данные
(TOTP и доступы к интеграциям) не восстановить, поэтому он лежит внутри архива бэкапа.

## Проверка перед обновлением

Перед обновлением старой панели выполните `nodeservice preflight` и `nodeservice backup`.
Первая команда только читает состояние и количество записей; вторая сохраняет БД и `.env`.
Архив нужно скопировать вне сервера. На версии, где `preflight` ещё нет, можно запустить
`infra/scripts/preflight.sh` из новой копии исходников с `NODESERVICE_DIR`, указывающим на старую установку.
Не заменяйте `ENCRYPTION_KEY` и `APP_SECRET` при обновлении. `nodeservice rollback` возвращает образ,
но не откатывает изменения БД; для восстановления данных используется сохранённый архив.

Отключённые старые метрики сохраняют отключённое состояние нового мониторинга, пока новые настройки
не сохранены явно. Исторические оплаты и ссылки на старые серверы сохраняются; соответствующие ноды
Remnawave выбираются вручную в редакторе записи биллинга. Совпадение IP не используется для автоматической привязки.

## Подключение нод

В разделе «Ноды» укажи URL панели Remnawave и API-ключ. NodeService обращается к Remnawave
по сети и получает состояние нод и доступные метрики. Устанавливать агент NodeService
на каждую ноду и открывать SSH-доступ для этого подключения не требуется.

## Переезд на другой сервер / восстановление с нуля

1. На старом сервере: `nodeservice backup` (или `nodeservice backup --to root@новый:/root`), скачать
   архив `nodeservice-backup-<время>.tar.gz`.
2. На чистом сервере одной командой:
   ```bash
   bash <(curl -fsSL https://raw.githubusercontent.com/feauche/nodeservice-panel/main/infra/scripts/install.sh) --restore /root/nodeservice-backup-<время>.tar.gz
   ```
   Установщик возьмёт секреты и данные из архива, домен предложит прежний.
   Сохранённое подключение Remnawave продолжит использоваться на новом сервере, если адрес
   панели Remnawave доступен с него.
3. Переключить A-запись домена на новый сервер. Сертификат Caddy выпустит сам.

Консольный `nodeservice backup` сохраняет БД и `.env`, но не данные Valkey (там только сессии входа).
Копия из панели может включать дополнительные файлы согласно выбранным настройкам. Замеры нод лежат
в базе и входят в копию вместе с ней.

## Время

Сервер живёт в UTC независимо от часового пояса машины: контейнеры api и postgres запускаются с
`TZ=UTC`, ночные задачи (`03:17` бэкап-разделы Журнала, `03:47` чистка) считаются по UTC, в API и
БД время хранится и отдаётся в ISO с `Z`. Браузер показывает всё в часовом поясе пользователя.
Расписание резервных копий из панели использует её настроенный часовой пояс.
Прежний cron бэкапа на хосте удаляется установщиком и скриптом обновления.

## Что растёт и как чистится

| Данные | Где | Срок | Как |
|---|---|---|---|
| Журнал | Postgres, `audit_log` по месяцам | `AUDIT_RETENTION_MONTHS` (12) | старые разделы удаляются целиком ночью |
| Решённые инциденты | Postgres | `INCIDENTS_RETENTION_DAYS` (365) | ночная чистка, открытые не трогаются |
| Замеры нод | Postgres, `remna_metric_samples` | 30 дней | очистка при записи замеров |
| Логи контейнеров | Docker json-file | 5 × 10 МБ на контейнер | ротация Docker |

Строки в Postgres лежат на диске, а не в памяти: сотни тысяч записей Журнала — это десятки мегабайт
на диске и постраничная выдача в панели, оперативную память они не занимают.
